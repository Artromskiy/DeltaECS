# Public API choice evaluation — 2026-10-16

Thirteen executable consumer tasks were given to four independent `gpt-6-luna` sessions at `high` reasoning effort. Two further fresh sessions repeated the dispatch and snapshot tasks after small public-documentation corrections. Runtime and generator implementations were not changed for this evaluation.

The result is mixed: twelve of thirteen original solutions passed the supplied base checkers after harness corrections, but two of those twelve failed additional correctness checks. The initial dispatch solution was correct but unnecessarily expensive. The snapshot task exposed both documentation friction and a generator limitation. This is evidence that the guide needs concrete lifetime and preparation examples, rather than evidence that every passing solution is optimal.

Other successful solutions sometimes retained a closure around a reusable operation; this is a cold allocation, not proof of a repeated per-entity delegate allocation. No timing is inferred for those wrappers.

The group checker includes overlapping groups, several CLR types, two float registrations and a tag. Group retrieval alone is insufficient to pass. ## Harness corrections and implementation findings

Two supplied checker defects were corrected independently of agent answers:

1. The health checker used a single target-typed `new(...)` in a `params` position that produced CS8752. Explicit `new ChangeNotice(...)` fixed the checker.
2. The tag checker invoked a generated static-lambda form from the global namespace. The generator emitted an invalid `using global::<global namespace>;`. Moving that checker helper into `ApiChoiceProbe` avoided this generator defect. No learner solution was rewritten to make the check pass. A duplicate-using warning remains in the generated path.

Their input-hash amendments are recorded in the artifact directory. The final baseline runs use the corrected checkers.

The snapshot investigation also independently reproduced a generator failure for a visitor method's open `T`: a typed `ForEachEntity` call emitted code referring to `T` outside its scope, producing CS0246. That implementation issue is not fixed by this documentation task. A public runtime generic functor is a working alternative for the same snapshot behavior.

## Documentation changes and fresh retests

The API grammar now:

- correctly identifies the entity-aware context-functor argument as `EntityRef`;
- gives an entity-aware open generic context-functor example and explains accessibility to generated code;
- distinguishes inferred generated view families from literal types usable in field declarations;
- explains retaining a terminal operation and one-time interface boxing without inventing `AsOperation()`.

The API-selection guide now distinguishes reusing a visitor object from preparing a typed handler per registration. It shows construction-time visitor dispatch and repeated handler lookup for point commands.

## Measured point-dispatch comparison

The benchmark compares the initial repeated-visitor strategy with a cold visitor that creates retained generic handlers. Both process 131,072 valid commands, alternating between two registered CLR types, using `IsAlive`, membership checks and typed `GetRef<T>` constrained mutation. Both have linear work in command count. Worlds and routing objects are prepared outside measurement; there are no change subscribers. Setup verifies the accepted-command count, while task 08 separately verifies mutation behavior.

| Strategy | Mean per 131,072 commands | Error, BDN default 99.9% interval | StdDev | Allocated |
| --- | ---: | ---: | ---: | ---: |
| Visitor dispatch on every command | 4.29ms | 17.1µs | 19.7µs | 0B |
| Prepared typed handler | 1.14ms | 8.20µs | 9.40µs | 0B |

Exact reported means were `4.291ms` and `1.140ms`: elapsed time fell by **73.4%**, or **3.76×** throughput for this batch. The intervals do not overlap. This supports the prepared-handler recommendation for this repeated-command workload, not a universal speedup for visitors or all point operations.

Environment: BenchmarkDotNet 0.15.8, Apple M4 Pro, Arm64 RyuJIT, .NET 10.0.12, SDK 11.0.100-rc.1.26425.128, macOS Tahoe 26.5.2. Settings: minimum iteration target 200ms, 10 warmups, 20 measurement iterations. BenchmarkDotNet could not set high process priority. Unity was idle, but macOS Storage Management was active around setup; this was one host/run and was not a background-free hardware study. Within-run standard deviations were approximately 0.46% and 0.82% of the means. No JIT instruction analysis was needed for this comparison.

The [benchmark source](dispatch-benchmark/Program.cs) and [run command](../README.md#performance-comparisons-and-documentation-changes) are retained. The benchmark measures routing after preparation, not creation cost, arbitrary invalid-command mixes, group cleanup, change observation or full snapshots.
