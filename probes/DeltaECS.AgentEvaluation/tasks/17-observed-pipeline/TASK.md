# Observe health changes and clean up defeated enemies

The solution receives a world and the health registration ID. It must retain one change observer for the lifetime of the solution. Each `Execute()` reports the health notifications since its previous call through the public `Changes` list as `ChangeNotice` values. An added or modified component records its current integer value; a removed component records `null`. Clear the list at the start of each call. The initial call reports the current baseline, and an unchanged repeated call reports nothing.

After collecting a call's notifications, remove the `Enemy` tag from every still-live entity that received an `Added` or `Modified` health notification in that call with a value at or below zero. Notifications for removed health are reported but do not select an entity for cleanup. Perform structural cleanup only after the retained observer has finished invoking its callbacks. This event-based cleanup is driven by the health changes in the current call; it does not revisit older health values. A later positive health write must leave any current `Enemy` tag in place. Do not destroy entities or alter health values. A removed notification may carry a stale handle. Component removal followed by re-addition and entity index reuse must keep old and new handles distinct, and notifications must follow the observer's documented coalescing rules.

Construct the solution once and reuse it. Do not rebuild an observer each call, read a removed component reference, or mutate structure from inside the observer callback. Do not hardcode entity IDs or enumerate `Scenario.Units` as the solution's entity source. Use only the supplied public documentation and consumer files. Explain the API choice, complexity, preparation and overhead in `CHOICE.md`; preserve the first implementation in `FIRST-Solution.cs.txt`; record attempts in `ATTEMPTS.md`; and run `dotnet run --project Consumer.csproj -c Release`. Do not edit the checker to make a solution pass.
